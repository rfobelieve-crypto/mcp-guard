# `prepare` 不是安裝期腳本——一個判定校準的提案

> 這是第二篇筆記。它不是外部事件，而是**這個工具自己的一條規則說了超出事實的話**。
>
> 依 `/trust` 的立場：對真實專案的不實指控，傷害不比漏報小。所以照樣寫出來。
>
> **本文只提出證據與選項，沒有修改 `checks.py`。** 偵測邏輯的判斷權在引擎維護者。

---

## 摘要

`checks.py` 把 npm 的五個生命週期腳本一視同仁地當成「安裝時會執行」：

```python
INSTALL_HOOKS = ("preinstall", "postinstall", "install", "prepare", "prepublish")
```

五者共用同一段說明：

> 「npm/pnpm 安裝過程就會執行這段指令——**你還沒使用它，程式碼已經跑過一次了**。
> 這是供應鏈投毒最常見的落點，務必逐字讀懂它在做什麼。」

**這句話對 `prepare` 與 `prepublish` 不成立。** 使用者從 npm registry 安裝套件時
（`npm i 套件`、`npx -y 套件`——也就是安裝 MCP 的標準方式），這兩個腳本**不會執行**。

實際資料中，這條規則有 **25 筆指向 `prepare`、僅 5 筆指向 `postinstall`**。
也就是說，**83% 的告警描述的是不會發生在使用者身上的事**。

---

## 一、npm 的實際語意

| Hook | 使用者 `npm i 套件` 時 | 開發者在專案根目錄 `npm install` | `npm publish` 前 | 安裝 git 依賴時 |
|---|---|---|---|---|
| `preinstall` | ✅ **會執行** | ✅ | — | ✅ |
| `install` | ✅ **會執行** | ✅ | — | ✅ |
| `postinstall` | ✅ **會執行** | ✅ | — | ✅ |
| `prepare` | ❌ **不會** | ✅ | ✅ | ✅ |
| `prepublish`（已棄用） | ❌ **不會** | ✅ | ✅ | — |

關鍵差別：**`prepare` 是給「準備發布這個套件」用的，不是給「安裝這個套件」用的。**
它的典型用途就是編譯（`npm run build`）與安裝 git hooks（`husky`）——
兩者都只在開發者的機器上有意義。

> **`prepare` 唯一會影響使用者的情況**：對方用 `npm i github:owner/repo`
> 這種 **git 依賴**的方式安裝。這種情況確實存在，所以這條規則不該直接刪掉，
> 只是措辭與嚴重度需要對應到正確的情境。

## 三、影響範圍（不誇大）

先講**沒有**被影響的部分：

- **不影響結論。** MEDIUM 不會讓專案從 🟢 變 🟡（判定只在 CRITICAL／HIGH 時升級）。
- **不影響總表的一句話摘要。** `top` 欄位取的是最嚴重的那一項，MEDIUM 不會浮上來。

實際被影響的是：

- **展開後的發現清單裡，有一段對這 25 個專案不成立的陳述。**
  `bytedance/UI-TARS-desktop`、`firebase/firebase-tools`、`ChromeDevTools/chrome-devtools-mcp`
  這些專案，因為用了 husky 這個業界標準工具，被告知「安裝時會自動執行腳本」、
  「這是供應鏈投毒最常見的落點」。
- **稀釋了真正該看的那 5 筆。** 使用者看到 30 筆「安裝期腳本」告警，
  其中 25 筆是雜訊，會降低對這個檢查項目的信任與注意力。

所以這是**陳述正確性與訊噪比**的問題，不是「判定錯誤」的問題。
規模中等，但落在一個以「證據可複現」為賣點的產品上，值得處理。

## 四、三種修法與取捨

### 選項 A：把 `prepare`／`prepublish` 拆成獨立規則，用正確措辭

```
標題：發布前置腳本：prepare（使用者安裝時不會執行）
嚴重度：LOW
說明：這段指令在開發者 clone 專案後執行 npm install、或以 git 依賴方式
      （npm i github:owner/repo）安裝時才會執行。從 npm registry 正常安裝
      的使用者不會碰到它。內容仍值得一看，但它不是安裝期的執行點。
```

- ✅ 陳述正確、保留資訊、真正的 `postinstall` 告警不再被稀釋
- ✅ git 依賴那個情境仍有提醒
- ⚠️ 需要新增一組文案與嚴重度對應

### 選項 B：只降嚴重度，維持現有措辭

- ✅ 改動最小
- ❌ **沒有解決核心問題**——不實的陳述還在，只是聲音變小

### 選項 C：維持現狀

- ✅ 零改動；理由是「多提醒總比漏提醒好」
- ❌ 與 `/trust` 的立場衝突：那一頁明說誤報的傷害不比漏報小，
  而且記錄過一次「防禦方被指控成攻擊方」的案例
- ❌ 25:5 的訊噪比會持續稀釋真正的 `postinstall` 告警

### 附帶建議（與上述獨立）

`preinstall`、`install`、`prepublish` 在 178 個專案中 **0 命中**。
不建議因此移除——它們是真實存在的攻擊面，只是目前樣本沒踩到，
這正是規則該涵蓋的東西。此處僅記錄，供評估規則覆蓋率時參考。

## 五、為什麼這份文件沒有附上修改

`checks.py` 是稽核引擎的偵測邏輯，`UX-TASK-BRIEF.md` 第 0 節明列為
**絕對不要動的部分**。而且上面三個選項之間的取捨牽涉產品判斷
（要多嚴、要不要為 git 依賴情境保留提醒），那是引擎維護者的決定，
不是前端這一側該替他做的。
