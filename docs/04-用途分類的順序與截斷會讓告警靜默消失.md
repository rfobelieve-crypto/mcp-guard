# 用途分類的順序與截斷，會讓告警靜默消失

> 第四篇筆記。與第三篇同樣是「工具說了超出事實的話」，但機制不同、方向也相反：
> 第三篇是**沒讀到程式碼卻說沒事**，這一篇是**讀到了，卻因為分類跑掉而收回警告**。
>
> **本文只提出證據與選項，沒有修改 `profile.py` 或 `checks.py`。** 判定邏輯的決定權在引擎維護者。
>
> 📌 **追記**：第七至九節補了五個案例（第九節那次**在同一次重掃裡同時出現兩個相反方向**），
> 確認這不是「偏保守」的偏差，而是跟著文案措辭走的震盪；十四天六次，是目前最主要的翻轉來源。
> **第十節把規模量出來：56 個「超出宣稱用途」旗標裡，只有 19 個的「宣稱用途」
> 是專案自己說的，其餘 37 個來自 README 前 2000 字。**
> 標題保留原名以免既有連結失效。

## 摘要

2026-08-15 的每日重掃讓 `bytebase/dbhub` 從 🟡 需人工複核 變成 🟢 未發現明顯風險。

它的程式碼沒有變少，自述也沒有改：

| 欄位 | 08-14 | 08-15 |
|---|---|---|
| `files` | 241 | **241**（相同） |
| `desc` | Token conscious database MCP server for Postgres, MySQL, SQL Server, MariaDB, SQLite. | **逐字相同** |
| `topics` | agents, ai, anthropic, claude, claude-ai, codex | **逐字相同** |
| `profile` | `database`（資料庫存取） | **`code`（程式碼／版控工具）** |
| `top` | ⚠ 會執行外部指令 / 開子行程（**超出**宣稱用途） | — |
| `high` | 1 | **0** |
| `verdict` | 🟡 需人工複核 | **🟢 未發現明顯風險** |

「會執行外部指令 / 開子行程」這個能力**從頭到尾都在**。它從 HIGH 掉到 LOW，
單純是因為我們把這個專案重新歸進了另一個用途類別——而在 `code` 這一類底下，
執行外部指令屬於預期能力。

**一項高風險告警，因為分類漂移而靜默消失了。**

## 一、為什麼分類會漂移

`profile.py` 的 `infer()` 把幾個欄位串成一個字串，然後**由上而下比對，第一個命中就回傳**：

```python
parts = [
    b.meta.get("description") or "",
    " ".join(b.meta.get("topics") or []),
    b.slug,
    b.npm_name,
]
# README 只取前段：後面通常是安裝說明與雜項，雜訊多
for path, text in b.files.items():
    if path.lower() in ("readme.md", ...):
        parts.append(text[:2000])
blob = " ".join(parts).lower()

for code, pattern, zh, caps in PROFILES:
    if re.search(pattern, blob, re.I):
        return code, zh, caps
```

兩個設計決定疊在一起，就產生了這個現象：

**（1）順序即優先權，而 `code` 排在 `database` 前面。**

`PROFILES` 的順序是：`…、devtool、code、filesystem、database、cloud、api、docs`。
`code` 的樣式是

```
\bgit\b|repositor|codebase|source code|static analys|decompil|ghidra|ide\b|程式碼
```

只要 blob 裡任何位置出現 `git`、`repository`、`codebase`，就會在輪到 `database`
之前先命中。而 `database`（`\bsql\b|postgres|mysql|sqlite|mongo|database|資料庫`）
即使在 `desc` 裡明明白白寫著，也永遠沒有機會被比到。

**（2）README 只取前 2000 字元，所以分類對「文字排在哪」敏感。**

`dbhub` 在 08-15 有推送。desc 與 topics 都沒動，slug 也沒動，
所以唯一可能改變 blob 的就是 README 前 2000 字元的內容——
只要一句 `git clone`、一個 repository 連結、一段 badge 往前挪進這 2000 字，
分類就會從 `database` 翻成 `code`。

**專案本身沒有變得更像程式碼工具，只是 README 的排版變了。**

## 二、不是單一個案：`database` 被遮蔽的規模

178 個專案的分類分布（**2026-08-15 當時的快照**，之後每天都會有幾個專案在類別之間移動，
數字請以最新的 `reports/data.json` 為準——會漂移這件事本身就是本文的主題）：

| profile | 專案數 |
|---|---|
| `devtool` 開發框架／工具鏈 | 42 |
| `api` 第三方 API 串接 | 38 |
| `code` 程式碼／版控工具 | 32 |
| `browser` 瀏覽器／網頁自動化 | 29 |
| `desktop` | 20 |
| `general` 未能明確判定 | 5 |
| **`database` 資料庫存取** | **4** |
| `docs` 文件／知識檢索 | 4 |
| `cloud` 雲端服務串接 | 4 |

`desc` 裡明確出現 `database|postgres|mysql|sqlite|mongo`、卻**沒有**被歸為
`database` 的專案有 3 個——相對於實際被歸為 `database` 的 4 個，這個比例不低：

```
🟡 timescale/pg-aiguide      → code
🟢 googleapis/mcp-toolbox    → devtool
🟢 bytebase/dbhub            → code
```

排在前面的 `devtool`（`\bsdk\b|framework|\blibrary\b|inspector|registry|toolbox|…`）
與 `code` 樣式都很寬，幾乎任何專案的 README 前段都可能命中，
所以順序在它們後面的類別實際上很難被選到。

## 三、為什麼這件事重要

意圖比對是這個產品的核心賣點——**同樣的能力，因為與自述用途不符而升級成 HIGH**。
`/registry` 上有 55 個專案帶著「超出宣稱用途」旗標（08-15 的數字，08-29 為 56），
那是最有價值的一批結論。

但這整套判斷建立在 `profile` 上。如果 `profile` 會因為 README 換行而改變，那麼：

- **同一個專案的結論會在 🟡 與 🟢 之間來回跳**，而它什麼都沒做。
- **消失的是警告，不是雜訊。** 這次少的是一項 HIGH。
- 使用者昨天看到「這個資料庫工具會執行系統指令，超出宣稱用途」，
  今天回來看變成「未發現明顯風險」——中間沒有任何解釋。

順帶一提，這與 08-12 的 `nowork-studio/NotFair` 是同一個機制的兩面：
那次是專案**真的改寫了 GitHub 描述**，`code → docs`，於是同一個能力從
符合宣稱用途變成超出宣稱用途（🟢→🟡）。那次分類改變是有依據的。
這次沒有——desc 與 topics 一字未改。

**同一個機制，一次給出有意義的訊號，一次給出雜訊。** 差別在於輸入是否穩定。

## 四、四種修法與取捨

### 選項 A：讓比對「取最佳」而非「取第一個」（建議）

計算每個 profile 的命中次數或權重，選分數最高的；平手時才用順序決定。

- ✅ `desc` 裡的 `database` 不會再被 README 裡偶然出現的一個 `git` 蓋過
- ✅ 對 README 排版的敏感度大幅下降
- ⚠️ 需要決定權重（`desc` 是否該比 README 重？多半應該）

### 選項 B：欄位分層，先看自述再看 README

先只用 `description` + `topics` 判一次；判不出來才把 README 拉進來。

- ✅ 最貼近「宣稱用途」的字面意義——README 是說明文件，`description` 才是自述
- ✅ 實作簡單，不必動樣式
- ⚠️ 沒有 description 的專案仍會落回原本的行為

### 選項 C：只調整 `PROFILES` 的順序

把 `database`、`filesystem` 這類具體的類別移到 `devtool`、`code` 之前。

- ✅ 改動最小
- ❌ **治標不治本**：first-match-wins 的脆弱性還在，只是換一批被遮蔽的類別

### 選項 D：讓 profile 變動本身成為一個訊號

profile 改變時，在報告裡註明「本次用途判定由 X 變為 Y，因此下列能力的
嚴重度隨之調整」。

- ✅ 不管分類準不準，至少**結論的變動是可解釋的**
- ✅ 與 A／B 併用最好
- ⚠️ 需要保存上一次的 profile 才能比對

### 附帶建議

不論選哪個，**因為 profile 改變而降級的告警，不應該無聲消失**。
使用者看得到的是「昨天 🟡 今天 🟢」，看不到中間發生了什麼。

## 五、為什麼這份文件沒有附上修改

`profile.py` 的推斷邏輯與 `checks.py` 的嚴重度判定都在
`UX-TASK-BRIEF.md` 第 0 節列為**絕對不要動的部分**。
而且上面四個選項牽涉產品判斷（要多敏感、要不要新增欄位、
首頁「超出宣稱用途」的數字會因此變動），那是引擎維護者的決定。

## 七、追加案例：同一個機制，這次反過來製造了假告警

2026-08-17 的每日重掃，`callstack/agent-device` 從 🟢 未發現明顯風險 變成
🟡 需人工複核，一次多出**兩項 HIGH**。

| 欄位 | 08-16 | 08-17 |
|---|---|---|
| `files` | 417 | **417**（相同） |
| `topics` | adb, agentic-ai, agents, ai-agents, android-emulator, automation | **逐字相同** |
| `desc` | CLI to control iOS and Android devices for AI agents | **改寫過**（見下） |
| `profile` | `browser`（瀏覽器／網頁自動化） | **`api`（第三方 API 串接）** |
| `high` | 0 | **2** |
| `verdict` | 🟢 未發現明顯風險 | 🟡 需人工複核 |

新增的兩項 HIGH 是：

```
⚠ 會讀寫本機檔案（超出宣稱用途）        ← 08-16 是「（符合宣稱用途）」LOW
⚠ 會執行外部指令 / 開子行程（超出宣稱用途）  ← 08-16 也是 LOW
```

**這兩項能力一項都沒有新增**，它們在 08-16 就都在，只是掛著「符合宣稱用途」。
變的同樣只有 `profile`。

### 觸發它的是哪一個字

新的 description 是：

> Mobile app automation and verification for AI coding agents. CLI, MCP server,
> and **typed Node.js API** for iOS, Android, HarmonyOS, TV, web, macOS, and Linux.

把 `desc + topics + slug` 丟進 `PROFILES` 比對：

```
08-16  命中：[]          ← 所以 browser 是從 README 前 2000 字來的
08-17  命中：['api']     ← 由 \bapi\b 命中
```

`api` 的樣式是 `\bapi\b|integration|connector|client for|wrapper|github|figma|…`。
命中的字就是 **`typed Node.js API` 裡的那個 `API`**——那是在講**這個套件自己
對外提供的程式介面**，不是在講「它去串接第三方 API」。兩件事在字面上長得一樣。

而 `api` 這一類的預期能力只有 `{NET, ENV}`。於是一個**裝置自動化工具**
（本來就要開子行程跑 adb、要寫暫存檔）被歸成「第三方 API 串接」之後，
它做本份的事全部變成越權。

### 為什麼這個案例值得單獨記

第一節的 `dbhub` 是**警告靜默消失**，這一個是**憑空長出兩項 HIGH**。
兩者是同一個 first-match-wins 機制的兩個方向：

- `dbhub`：`desc` 裡明講 database，卻被排在前面的 `code` 攔截 → 少了一項 HIGH
- `agent-device`：`desc` 裡的 `API` 是自述用詞，被 `api` 這一類接收 → 多了兩項 HIGH

**所以這個機制不是「保守」的。** 它不會固定往安全或往嚴格的一邊偏，
而是跟著文案措辭亂走。`/trust` 那一頁寫得很清楚：對真實專案的不實指控，
傷害不比漏報小——這次就是不實指控那一種。

順帶一提，這個案例也暴露了另一件事：**`PROFILES` 裡沒有「裝置／App 自動化」
這一類**。`browser` 只是碰巧涵蓋了它（因為 README 裡有 playwright 之類的字），
不是真的判對。08-16 那個 🟢 其實是「用錯的理由得到對的結論」。
第四節的選項 A／B 能減少震盪，但這一格的空缺要另外補。

## 八、第三個案例：一週內第三次，而且又是掉進 `api`

2026-08-22 的每日重掃，`zereight/gitlab-mcp` 從 🟢 變成 🟡，同樣一次多出兩項 HIGH。

| 欄位 | 08-21 | 08-22 |
|---|---|---|
| `desc` | First gitlab mcp for you, building together | **逐字相同** |
| `topics` | （空） | **相同** |
| `files` | 302 | 314（專案當天有推送） |
| `profile` | `browser`（瀏覽器／網頁自動化） | **`api`（第三方 API 串接）** |
| `high` | 0 | **2** |
| `verdict` | 🟢 未發現明顯風險 | 🟡 需人工複核 |

新增的兩項一樣是「會讀寫本機檔案」與「會執行外部指令 / 開子行程」，
08-21 都標著「（符合宣稱用途）」。`desc` 與 `topics` 一字未改，
所以改變分類的又是 README 前 2000 字。

### 這一次比較微妙：新分類其實比舊分類合理

`gitlab-mcp` 包的就是 GitLab 的 REST API，歸成「第三方 API 串接」說得過去；
反倒是 08-21 的 `browser` 明顯不對（多半是 README 裡出現了 playwright 之類的字）。
換句話說**這次是從一個錯的分類跳到一個比較對的分類**——但跳動的原因不是有人做了判斷，
而是文字位置變了。結論會不會正確，取決於運氣。

### 順帶查到一件具體的事：`\bgit\b` 抓不到 `gitlab`

`code` 這一類的樣式開頭是 `\bgit\b`，而詞界讓它**對不上 `gitlab`、`github`、`gitea`**：

```
\bgit\b vs 'git'      → True
\bgit\b vs 'gitlab'   → False
\bgit\b vs 'github'   → False
\bgit\b vs 'gitea'    → False
```

所以以這些平台命名的版控類 MCP，除非 README 裡剛好另外出現 `repositor`／`codebase`，
否則**永遠進不了 `code`**。更巧的是 `api` 的樣式裡直接列了 `github`，
於是「GitHub 工具」會優先被認定成「第三方 API 串接」而不是「程式碼／版控工具」。

目前 178 個專案裡，slug 或 desc 含 `gitlab|github|gitea` 卻不在 `code` 的有 3 個
（`zereight/gitlab-mcp` → api、`mcparmory/registry` → devtool、
`uptimemonitoring/examples` → desktop；後兩個屬於順帶命中，不是版控工具）。
規模不大，但成因很明確，而且與第四節的選項 A／B 是同一件事的兩面：
**樣式本身也需要檢查，不只是比對順序。**

### 為什麼把三次寫在一起

| 日期 | 專案 | 方向 | 觸發原因 |
|---|---|---|---|
| 08-15 | `bytebase/dbhub` | 少一項 HIGH（🟡→🟢） | README 排版變動，`code` 蓋過 `database` |
| 08-17 | `callstack/agent-device` | 多兩項 HIGH（🟢→🟡） | desc 改寫，`typed Node.js API` 的 `API` 命中 `api` |
| 08-22 | `zereight/gitlab-mcp` | 多兩項 HIGH（🟢→🟡） | README 變動，`browser` → `api` |

一週三次，而且**這是目前唯一反覆出現、既不是真的程式碼變動、也不是門檻到期的翻轉來源**。
其餘每日重掃多半是 0 筆翻轉。分類漂移不是偶發雜訊，是這個資料集裡最主要的不穩定因子。

## 九、同一次重掃，兩個方向同時發生

2026-08-26 的每日重掃（跨 UTC 午夜於 08-27 00:33 推送）一次出現**兩筆翻轉，
方向相反，而且都是分類漂移**。這是目前最乾淨的一組對照。

| 專案 | 判定 | `profile` | `high` | `files` | `desc` |
|---|---|---|---|---|---|
| `anypost/emailmd` | 🟢→**🟡** | `browser`→**`api`** | 0→**2** | 176→197 | 逐字相同 |
| `blazickjp/arxiv-mcp-server` | 🟡→**🟢** | `api`→**`devtool`** | 2→**0** | 96→**96**（相同） | 逐字相同 |

兩個專案的自述都一字未改，變的都只有 `profile`。
一個憑空多出兩項 HIGH，一個靜默少掉兩項 HIGH——**在同一次重掃裡**。

到這裡已經不需要再論證方向性了：這個機制既不偏嚴也不偏鬆，它只是跟著
README 前 2000 字的排版走。而且兩次都以 `api` 為樞紐——進入 `api` 就升級，
離開 `api` 就降級，因為 `api` 的預期能力集合（`{NET, ENV}`）比鄰近類別都窄。

### `arxiv-mcp-server` 特別值得看

它的 `files` 連數字都沒變（96→96），連程式碼都沒動過，
少掉的兩項是「會執行外部指令 / 開子行程」與「會讀寫本機檔案」。

而把它的 `desc + topics + slug` 單獨丟進 `PROFILES` 比對：

```
desc: A Model Context Protocol server for searching and analyzing arXiv papers
topics: ai, arxiv, claude-ai, gpt, llm, mcp-server

命中：['docs']        ← 文件／知識檢索
實際 profile：08-25 api、08-26 devtool
```

**它的自述明確指向 `docs`（文件／知識檢索），而那大概就是正確答案**——
一個搜尋與分析 arXiv 論文的伺服器，本來就是知識檢索工具。
但 `docs` 排在 `PROFILES` 最後一個，只要 README 前段出現任何
`api`／`sdk`／`framework`／`toolbox` 之類的字就永遠輪不到它。
於是這個專案在 `api` 與 `devtool` 之間來回跳，而正確的那一格從來沒被選中過。

最直接的證據：在這個案例裡，只看自述就會得到比現況更好的答案。

## 十、量化：56 個「超出宣稱用途」裡，只有 19 個站在自述上

2026-08-29 的重掃出現第六次同型翻轉：`amruthpillai/reactive-resume`
`api`→`code`、🟡→🟢、少一項 HIGH，`files` 420→420、`desc` 逐字未改。

這次沒有新的機制，所以與其再記一個案例，不如把**規模**量出來。
問題其實可以問得很簡單：**每個專案的 `profile`，究竟是它自己說的，還是 README 排版說的？**

把 `desc + topics + slug`（不含 README）單獨丟進 `PROFILES` 比對，178 個專案分成三類：

| 分類的依據 | 專案數 |
|---|---|
| 自述**完全沒有**命中任何樣式 → 分類 100% 由 README 前 2000 字決定 | **72（40%）** |
| 自述有命中，但最終 `profile` 不在命中清單裡 → README 蓋過了自述 | 35（20%） |
| 最終 `profile` 與自述一致 | 71（40%） |

也就是說 **178 個裡有 107 個（60%）的用途判定，實際上不是由專案的自述決定的。**

### 對核心賣點的影響

真正要緊的是這一格。`/registry` 上帶著「超出宣稱用途」旗標的 56 個專案——
那是這個產品最有價值、也最常被引用的一批結論——按同樣的三分法拆開：

| 「超出宣稱用途」的分類依據 | 專案數 |
|---|---|
| 自述完全沒訊號，分類全靠 README | **31** |
| 自述有訊號，但最終分類與它不符 | 6 |
| 最終分類與自述一致 | **19** |

**56 項裡只有 19 項，其「宣稱用途」是專案自己說出來的。**

這不表示另外 37 項一定判錯——它們很可能是對的。
但「超出**宣稱**用途」這句話的說服力，完全來自「宣稱」二字：
使用者理解的是「這個專案自己說它要做 X，卻要了 X 以外的權限」。
當那個 X 其實是從 README 開頭 2000 字裡撈出來的關鍵字時，
這句話的字面意思與實際成立的依據就有落差。

而第七至九節已經證明，README 前 2000 字是個會晃動的輸入：
十四天六次翻轉，其中五次專案的自述一個字都沒改。

### 這讓第四節的選項 B 從「比較好」變成「可量測」

選項 B（先用 `description` + `topics` 判一次，判不出來才看 README）在這個資料集上
會有明確的效果：71 個目前就與自述一致的專案不受影響；35 個被 README 蓋過的會回到
自述指向的類別；72 個自述沒訊號的則會落到 `general`（或維持現行的 README 後備）——
**而後面這 72 個正好就是最該被標成「用途無法從自述判定」的一批。**

如果願意接受首頁「超出宣稱用途」的數字下修，選項 B 換來的是：
**留下的每一項，都能指著專案自己的一句話說「它自己是這樣寫的」。**

### 自己複現

```bash
python3 -c "
import json,re,sys; sys.path.insert(0,'.')
from mcp_guard.profile import PROFILES
d=json.load(open('reports/data.json'))
flag=lambda p: any('超出宣稱用途' in f['title'] for f in p.get('findings',[]))
def bucket(p):
    blob=' '.join([p.get('desc') or '',' '.join(p.get('topics') or []),p['slug']]).lower()
    hits=[x for x,pat,zh,cs in PROFILES if re.search(pat,blob,re.I)]
    return '自述無訊號' if not hits else ('被README蓋過' if p.get('profile') not in hits else '與自述一致')
import collections
print('全部  ', collections.Counter(bucket(p) for p in d['projects']))
print('超出的', collections.Counter(bucket(p) for p in d['projects'] if flag(p)))
"
```
